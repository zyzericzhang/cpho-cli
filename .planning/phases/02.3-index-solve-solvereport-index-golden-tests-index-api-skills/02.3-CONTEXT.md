# Phase 02.3: Index 读写分离 + Solve 降级 - Context

**Gathered:** 2026-05-24
**Status:** Ready for planning

## Phase Boundary

Phase 02.3 交付四项相互关联的重构：

1. **切断 SolveReport → index 管线耦合** — 移除 `builder.py` 对 SolveReport 的加载和标签提取，OCR_FALLBACK 成为唯一标签源。
2. **删除 golden_tests + cpho eval** — 全部删除 golden_tests 目录、eval 框架代码和 CLI 命令。不做自动化回归，用户手动验证。
3. **index 标签读写 API** — 新增 Python API + CLI 子命令，skills 可以读写 index 标签。`user_tags` 与 `llm_tags` 分离存储，provenance 追踪每次写入。
4. **solve 降级为真正的 builtin skill** — `solve_problem()` 硬编码逻辑替换为通过 `SkillRuntime` 执行 `builtin_skills/solve/skill.yml` 定义的 7 步 DAG。

**这不是 Phase 3 的 skill 系统建设。** solve 接入 SkillRuntime 是为了验证 runtime 本身的可用性，为 Phase 3 的 explain/quiz skill 铺路。

## Implementation Decisions

### SolveReport 解耦

- **D-01:** 直接删除耦合代码，不引入中间 enrichment abstraction。先解耦验证 OCR-only 基线 → 再实现读写 API。
- **D-02:** 删除范围：
  - `core/index/builder.py`: `_load_solve_report()`、`_solve_report_tag_dict()` 函数，`SolveReport` import
  - `core/index/builder.py:328`: `refine_tags()` 调用不再传入 `solve_report_tags`
  - `core/index/tagging.py`: `refine_tags()` 签名移除 `solve_report_tags` 参数，prompt 模板不再引用 SolveReport 标签
  - `models/index.py`: 移除 `TagSource.SOLVE_REPORT` 枚举值，移除 `IndexEntry.solve_report_path` 字段

### 标签读写 API

- **D-03:** Python API 核心 + CLI 薄包装。`core/index/api.py` 新增函数：
  - `add_problem_tags(problem_id, tags, skill_name, reasoning)` — 追加标签，带 provenance
  - `remove_problem_tags(problem_id, tags)` — 移除指定标签
  - `update_problem_tags(problem_id, tags, skill_name, reasoning)` — 替换全部 user_tags
- **D-04:** CLI 子命令 `cpho index tag-add` / `tag-remove` / `tag-set` 是上述 Python API 的薄包装。遵循芯-壳分离模式。

### 标签分离存储 + Provenance

- **D-05:** `IndexEntry` 数据模型重构：
  - 现有 `physics_model_tags`、`math_technique_tags`、`heuristic_tags`、`difficulty_aspects` 归入 `llm_tags` 概念组（LLM 机打，`cpho index` 写入）
  - 新增 `user_tags: list[UserTagEntry]` 字段（skill/用户写入，`cpho index` 不覆盖）
- **D-06:** `UserTagEntry` 结构：`{tags: list[str], skill_name: str, timestamp: datetime, reasoning_snippet: str}`。provenance 记录哪个 skill、什么时间、基于什么推理。
- **D-07:** skill 可写入任意标签。匹配 vocabulary 的标记为 `canonical`，不匹配的标记为 `unverified`。vocabulary 管理员后续可将 `unverified` 提升为 canonical。Phase 02.3 只实现数据模型和写入逻辑，不实现提升 UI。

### 重建行为

- **D-08:** `cpho index --force` 只重建 LLM 机打标签（`llm_tags` 组），不动 `user_tags`。
- **D-09:** 新增 `cpho index --force-all` 清空所有标签（包括 `user_tags`）做完全重置。

### golden_tests + eval 移除

- **D-10:** 全部删除：
  - `golden_tests/` 整个目录（含 `sample_mechanics/` 和 `splitting/`）
  - `core/eval.py` + `models/eval.py`
  - CLI `cpho eval` 命令和 import
- **D-11:** `test_splitting_golden.py` 需适配——将其引用的 splitting 测试数据移入 `tests/fixtures/` 或重构测试不依赖 golden_tests 目录。

### solve 降级为 builtin skill

- **D-12:** `solve_problem()` 硬编码逻辑替换为通过 `SkillRuntime` 执行 `builtin_skills/solve/skill.yml` 的 7 步 DAG。OCR handler 和 LLM handler 复用 core 现有 provider 抽象。
- **D-13:** `cpho solve` CLI 命令改为 skill runtime 调用的薄包装。命令行接口保持不变（`cpho solve problem.pdf --answer answer.pdf`），内部改为 skill 执行。
- **D-14:** 现有的 `SkillRuntime` 可能需要增强以支持 solve 的 7 步 DAG 实际执行（如 `python_tool` handler 的实现、LLM handler 与 `core/llm.py` 的对接）。这些增强是 Phase 02.3 的范围——solve 是 SkillRuntime 的第一个真实验证案例。

### 测试策略

- **D-15:** 不做自动化回归验证。单元测试覆盖 API 正确性（fake providers）。用户手动运行 solve 并检查输出质量。Phase 3 的 explain/quiz skill 会驱动重新设计更通用的 eval 框架。

### Claude's Discretion

- `user_tags` vs `llm_tags` 在 IndexEntry 中的具体字段结构和命名由 planner 根据现有 Pydantic 模式决定。
- CLI 子命令的具体参数设计（`--problem-id`、`--tags`、`--skill-name` 等）由 planner 根据现有 CLI 风格决定。
- `test_splitting_golden.py` 的处理方式（迁移 fixtures vs 重写）由 planner 决定。
- checkpoint JSON schema 和 DISCUSSION-LOG.md 模板的选择无需用户介入。

## Existing Code Insights

### Reusable Assets
- `core/runtime.py` 的 `SkillRuntime` — 完整 DAG 执行引擎，solve 直接使用
- `core/skills.py` 的 `load_skill()` — YAML → SkillSpec 加载，已验证可用
- `builtin_skills/solve/skill.yml` + `prompts/` — solve 的 DAG 定义和 6 个 prompt 模板已存在
- `core/index/api.py` 的 `query_index`/`get_problem_entry` — 读写 API 的同级扩展点
- `core/index/storage.py` 的 JSONL 原子写入 — 标签写入可复用

### Established Patterns
- **芯-壳分离**: 标签 API 在 `core/index/api.py`，CLI 在 `cli/app.py` 做薄包装
- **Pydantic StrictModel**: 所有数据模型使用 Pydantic，标签写入参数使用 StrictModel 校验
- **handler 注册模式**: SkillRuntime 的 `handlers` dict 模式，solve 的 LLM/python_tool handler 遵循同一模式
- **中文 UX**: 用户界面默认中文

### Integration Points
- **Phase 3 explain/quiz skills** → 复用 Phase 02.3 建立的 SkillRuntime + handler 模式，以及标签读写 API
- **Phase 3 skill 注册** → Phase 02.2 的 Command registry（`commands/builtin_skills.py` 预留注册点）接收 solve/explain/quiz Command
- **Phase 4 knowledge graph** → 基于 `user_tags` 中的标签关联题目

## Specific Ideas

- solve 接入 SkillRuntime 后，trace 输出写入 `.cpho/traces/solve/` 目录，每个 problem 一个 JSONL 文件，遵循 runtime 的 TraceRecord schema
- CLI `cpho index tag-add` 的交互体验参考 `cpho index` 的 quiet 模式——默认显示操作摘要，`--quiet` 静默
- `user_tags` 在 `/show` REPL 命令中展示时，显示 skill 名称和时间戳，和 llm_tags 视觉区分（如 `[solve 2026-05-24] 牛顿定律, 能量守恒`）
