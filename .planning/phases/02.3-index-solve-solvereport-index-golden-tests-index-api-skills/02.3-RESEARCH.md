### Locked Decisions

#### SolveReport 解耦

- **D-01:** 直接删除耦合代码，不引入中间 enrichment abstraction。先解耦验证 OCR-only 基线 → 再实现读写 API。
- **D-02:** 删除范围：
  - `core/index/builder.py`: `_load_solve_report()`、`_solve_report_tag_dict()` 函数，`SolveReport` import
  - `core/index/builder.py:328`: `refine_tags()` 调用不再传入 `solve_report_tags`
  - `core/index/tagging.py`: `refine_tags()` 签名移除 `solve_report_tags` 参数，prompt 模板不再引用 SolveReport 标签
  - `models/index.py`: 移除 `TagSource.SOLVE_REPORT` 枚举值，移除 `IndexEntry.solve_report_path` 字段

#### 标签读写 API

- **D-03:** Python API 核心 + CLI 薄包装。`core/index/api.py` 新增函数：
  - `add_problem_tags(problem_id, tags, skill_name, reasoning)` — 追加标签，带 provenance
  - `remove_problem_tags(problem_id, tags)` — 移除指定标签
  - `update_problem_tags(problem_id, tags, skill_name, reasoning)` — 替换全部 user_tags
- **D-04:** CLI 子命令 `cpho index tag-add` / `tag-remove` / `tag-set` 是上述 Python API 的薄包装。遵循芯-壳分离模式。

#### 标签分离存储 + Provenance

- **D-05:** `IndexEntry` 数据模型重构：
  - 现有 `physics_model_tags`、`math_technique_tags`、`heuristic_tags`、`difficulty_aspects` 归入 `llm_tags` 概念组（LLM 机打，`cpho index` 写入）
  - 新增 `user_tags: list[UserTagEntry]` 字段（skill/用户写入，`cpho index` 不覆盖）
- **D-06:** `UserTagEntry` 结构：`{tags: list[str], skill_name: str, timestamp: datetime, reasoning_snippet: str}`。provenance 记录哪个 skill、什么时间、基于什么推理。
- **D-07:** skill 可写入任意标签。匹配 vocabulary 的标记为 `canonical`，不匹配的标记为 `unverified`。vocabulary 管理员后续可将 `unverified` 提升为 canonical。Phase 02.3 只实现数据模型和写入逻辑，不实现提升 UI。

#### 重建行为

- **D-08:** `cpho index --force` 只重建 LLM 机打标签（`llm_tags` 组），不动 `user_tags`。
- **D-09:** 新增 `cpho index --force-all` 清空所有标签（包括 `user_tags`）做完全重置。

#### golden_tests + eval 移除

- **D-10:** 全部删除：
  - `golden_tests/` 整个目录（含 `sample_mechanics/` 和 `splitting/`）
  - `core/eval.py` + `models/eval.py`
  - CLI `cpho eval` 命令和 import
- **D-11:** `test_splitting_golden.py` 需适配——将其引用的 splitting 测试数据移入 `tests/fixtures/` 或重构测试不依赖 golden_tests 目录。

#### solve 降级为 builtin skill

- **D-12:** `solve_problem()` 硬编码逻辑替换为通过 `SkillRuntime` 执行 `builtin_skills/solve/skill.yml` 的 7 步 DAG。OCR handler 和 LLM handler 复用 core 现有 provider 抽象。
- **D-13:** `cpho solve` CLI 命令改为 skill runtime 调用的薄包装。命令行接口保持不变（`cpho solve problem.pdf --answer answer.pdf`），内部改为 skill 执行。
- **D-14:** Phase 02.3 需要实现两个 handler 以让 SkillRuntime 真正可运行：
  - **`llm` handler**: 渲染 Jinja2 prompt 模板 → 调用 `provider.complete()`（支持多模态消息格式，见 D-17）→ JSON 解析输出 → 写入 blackboard。复用于所有 skill（solve 的 step 2-7 全部用此 handler）。
  - **`python_tool` handler**: 内置黑板书签——从 blackboard 取值、做字符串/数据变换、写回 blackboard。**不做外部工具调用或 Python 沙箱**（Phase 3 再扩展）。solve 的 step 1 (`extract_problem_answer`) 用此 handler 拆分题目和答案文本。

#### 测试策略

- **D-15:** 不做自动化回归验证。单元测试覆盖 API 正确性（fake providers）。用户手动运行 solve 并检查输出质量。Phase 3 的 explain/quiz skill 会驱动重新设计更通用的 eval 框架。

#### 多模态输入 + 模型能力检测

- **D-16:** OpenRouter [Universal PDF Support](https://openrouter.ai/announcements/universal-pdf-support) 作为多模态 PDF 的后端。PDF 通过 OpenRouter 自动处理——对 Gemini/Anthropic/OpenAI 等原生多模态模型直发 PDF，对其他模型自动 OCR 转文本。**客户端不需要自己做 PDF→图片转换。**
- **D-17:** `core/llm.py` 的 `complete()` 方法支持多模态消息格式。`content` 字段支持 list 类型（`text` + `image_url` 混合），兼容 OpenAI Vision API 格式：
  ```python
  messages=[{"role": "user", "content": [
      {"type": "text", "text": "Solve this problem:"},
      {"type": "image_url", "image_url": {"url": "data:image/png;base64,..."}},
  ]}]
  ```
- **D-18:** 模型能力检测双层机制：
  - **启动时（session 级）**: 加载 provider config 时检测当前模型是否支持 vision。通过 OpenRouter model metadata 或已知支持列表判断。缓存结果到 session。
  - **skill 执行时**: llm handler 根据 `blackboard` 中是否有 image/pdf 引用 + 模型是否 support_vision 自动选择路径（多模态直发 or OCR 降级为纯文本）。
  - **切换 provider 时**: `cpho repl` 中 `/set provider <name>` 时重新检测模型能力。
- **D-19:** 所有 skill（solve、explain、quiz 等）统一受益于 llm handler 的多模态能力。handler 不区分 skill 类型，只根据输入数据格式 + 模型能力自动路由。
- **D-20:** `cpho index` 默认仍用 OCR 路径（保持确定性和低成本），新增 `--vision` 选项显式开启多模态索引路径。`--vision` 仅对支持多模态的模型生效。
- **D-21:** 多模态支持的图片格式：PNG、JPEG、WEBP、GIF（非动图）。PDF 通过 OpenRouter 自动处理（`mistral-ocr` 引擎 $2/千页，或 `pdf-text` 引擎免费）。单张图片/文件上限由下游模型决定（通常 20MB）。

## Summary

Phase 02.3 should be planned as a narrow schema-and-runtime refactor, not as Phase 3 skill system expansion. The current code still has explicit `SolveReport` coupling in `builder.py`, `tagging.py`, the tag prompt, `models/index.py`, and tests; deleting those references is straightforward, but old JSONL rows will become stale under the strict Pydantic model and must be handled deliberately. [VERIFIED: codebase grep + `src/cpho_cli/core/index/builder.py:58`, `src/cpho_cli/core/index/builder.py:76`, `src/cpho_cli/core/index/builder.py:370`, `src/cpho_cli/core/index/tagging.py:30`, `src/cpho_cli/core/index/tagging.py:268`, `src/cpho_cli/models/index.py:40`, `src/cpho_cli/models/index.py:135`]

The smallest safe index model change is to keep the existing canonical LLM tag fields as the "LLM tag group" for compatibility, add `user_tags: list[UserTagEntry]`, remove `solve_report_path`, remove `TagSource.SOLVE_REPORT`, and bump `TAG_SCHEMA_VERSION`. This satisfies tag read/write separation while avoiding a broad query API rewrite. [VERIFIED: `src/cpho_cli/models/index.py:122-139`, `src/cpho_cli/core/index/api.py:12-89`; ASSUMED: treating existing top-level tag buckets as the `llm_tags` concept rather than nesting them]

Multimodal input should be implemented inside the shared LLM handler and provider abstraction, not inside `solve_problem()` or index-specific code. OpenRouter documents images as message content blocks using `image_url`, but PDFs use a `file` content block with `file_data`; model capability detection can use `/api/v1/models` and `architecture.input_modalities`. [CITED: https://openrouter.ai/docs/features/images-and-pdfs] [CITED: https://openrouter.ai/docs/api-reference/list-available-models] [VERIFIED: live OpenRouter models API via curl]

**Primary recommendation:** Plan five slices in order: remove SolveReport/index coupling, add user tag schema + read/write API + CLI, delete eval/golden_tests while migrating splitting fixtures, wire solve through `SkillRuntime` with minimal `llm`/`python_tool` handlers, then add multimodal routing and `cpho index --vision`. ## Common Pitfalls

### Pitfall 1: Strict JSONL Breakage After Removing Fields

**What goes wrong:** `load_index()` validates each line directly into `IndexEntry`, so old rows with `solve_report_path` or `source="solve_report"` can raise validation errors after the model changes. [VERIFIED: `src/cpho_cli/core/index/storage.py:22-30`; VERIFIED: `src/cpho_cli/models/config.py:6-7`]

**Why it happens:** `StrictModel` forbids extra fields, and removing enum variants invalidates old persisted values. [VERIFIED: `src/cpho_cli/models/index.py:38-42`, `src/cpho_cli/models/index.py:122-139`]

**How to avoid:** Bump `TAG_SCHEMA_VERSION`, update `load_existing_index_for_rebuild()` coverage, and wrap normal `load_index()` stale-schema failures in a clear `IndexBuildError` or `IndexNotFoundError`-style message. [VERIFIED: `src/cpho_cli/core/index/hashing.py:17-18`; VERIFIED: `src/cpho_cli/core/index/storage.py:39-62`]

**Warning signs:** Tests fail with `ValidationError` mentioning unknown `solve_report_path` or invalid enum `solve_report`. [ASSUMED]

### Pitfall 2: `--force` Accidentally Deletes Skill/User Tags

**What goes wrong:** Current force logic sets action to `re_ocr_and_re_tag` and constructs a fresh `IndexEntry`; without explicit copying, new `user_tags` will be lost. [VERIFIED: `src/cpho_cli/core/index/builder.py:327-333`, `src/cpho_cli/core/index/builder.py:414-435`]

**Why it happens:** The existing model has no user tag field, so current builder code never had to preserve it. [VERIFIED: `src/cpho_cli/models/index.py:122-139`]

**How to avoid:** Add `force_all: bool = False`; copy `old.user_tags` into replacement entries when `force_all` is false; test `--force` and `--force-all` separately. [VERIFIED: CONTEXT.md D-08/D-09]

**Warning signs:** A test that seeds `user_tags`, calls `build_index(force=True)`, and reloads the index returns an empty `user_tags` list. [ASSUMED]

### Pitfall 3: PDF Payload Shape Confusion

**What goes wrong:** Images use `image_url`, but PDFs use `file`/`file_data`; sending a PDF as `image_url` is not the documented OpenRouter PDF path. [CITED: https://openrouter.ai/docs/features/images-and-pdfs]

**Why it happens:** D-17 correctly describes OpenAI-compatible image content, while D-16/D-21 require OpenRouter Universal PDF support. [VERIFIED: CONTEXT.md D-16/D-17/D-21; CITED: OpenRouter docs]

**How to avoid:** Build a helper that maps suffix/MIME to content block type: images to `image_url`, PDFs to `file`, unsupported image formats to OCR fallback. [CITED: OpenRouter docs; ASSUMED: helper design]

**Warning signs:** OpenRouter returns 400 errors for malformed content blocks or provider-specific unsupported file input. [ASSUMED; VERIFIED: local REPL log contains 400 provider errors for other capability mismatches]

### Pitfall 4: Capability Detection Only Checks "Vision"

**What goes wrong:** A model can support image but not file input, or support multimodal input but not tools/structured outputs. [VERIFIED: live OpenRouter models API showed `openai/gpt-4o-mini` input modalities include `text`, `image`, `file`; `deepseek/deepseek-chat` input modalities include `text` only]

**Why it happens:** "Vision" is too coarse for PDF, image, tool calling, and structured JSON behavior. [CITED: OpenRouter models docs]

**How to avoid:** Cache a capability object with `input_modalities`, `supported_parameters`, and conservative fallbacks; make the LLM handler route by required input type and response mode. [CITED: OpenRouter models docs; ASSUMED: implementation shape]

**Warning signs:** `/set provider` or `--provider` changes cause the same skill to fail on tool choice, structured output, or multimodal payload. [VERIFIED: local REPL log]

### Pitfall 5: Deleting `golden_tests/` Breaks Splitting Regression

**What goes wrong:** `tests/test_splitting_golden.py` imports fixtures from `golden_tests/splitting`; deleting `golden_tests/` without moving those files breaks tests unrelated to eval. [VERIFIED: `tests/test_splitting_golden.py:14-19`]

**Why it happens:** `golden_tests/` contains both eval cases and a splitting fixture. [VERIFIED: `rg --files golden_tests`]

**How to avoid:** Move `golden_tests/splitting/*` into `tests/fixtures/splitting/` before deleting the directory, then update the test path. [VERIFIED: CONTEXT.md D-11]

**Warning signs:** Pytest fails with missing `ipho_style_multi_problem.expected.json` or PDF fixture paths. [VERIFIED: `tests/test_splitting_golden.py:14-29`]
