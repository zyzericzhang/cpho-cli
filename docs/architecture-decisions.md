# 架构决策记录

> 记录项目早期 exploration 阶段已明确的方向性决策。
> 具体技术选型（用什么库、什么框架）不在本文档范围内——那是 research 和 spike 阶段的产出。

---

## 1. 产品形态：纯本地 CLI 优先

**决策**：第一个可用版本是纯本地命令行工具，不依赖线上后端。

**Why**：绕过线上题库建设的后端复杂度，快速验证核心假设（更多题目上下文 + agent 编排 = 更好解析质量）。
调试解析质量不应该被前端 UI 开发阻塞。

**How to apply**：任何解析质量的迭代，优先在 CLI 环境验证。确认有效后再考虑同步到线上平台。

---

## 2. 架构模式：芯-壳分离

**决策**：业务逻辑（core）与界面层（CLI）严格分离。core 不依赖任何界面框架，CLI 是薄适配层。

**Why**：CLI 和线上平台终将共享同一套解析逻辑。如果 core 和 CLI 耦合，未来做 Web 适配时要么重写，要么复制粘贴——这是最常见的失败模式。

**How to apply**：core 层不 import CLI 框架，不直接 print/input。所有 I/O 通过抽象接口注入。

---

## 3. 技术生态：Python

**决策**：使用 Python 作为主要开发语言。

**Why**：AI/LLM 工具链（prompt 模板、模型路由、结构化输出、agent 编排）在 Python 生态中远成熟于其他语言。
现有线上平台是 TypeScript，但线上不需要运行 CLI 的 core——两者通过 API 和文档同步，不共享代码运行时。

**How to apply**：项目零 Node.js 依赖。core 保持纯 Python，方便分发和复用。

---

## 4. 基座策略：基于现有框架定制，不从头造

**决策**：在成熟的 Python agent CLI 框架上定制和扩展，不做 greenfield 开发。

**Why**：prompt 模板插值、模型路由、结构化 JSON 提取、重试机制——这些基础能力社区已经打磨多年。
自己写不仅浪费时间，还会踩一遍已知的坑。

**待调研**：具体选哪个框架（调研问题见 research-questions.md）。

---

## 5. 参数调试模式：配置文件驱动 + 人工对比

**决策**：通过 YAML 配置文件控制所有可调参数。实验记录存为 JSONL。用户自己对比输出结果判断好坏。

**Why**：目标用户（教练、开发者）有能力自己判断解析质量。不需要引入 LLM-as-Judge 的额外复杂度和成本。
YAML 可读可版本控制，JSONL 可 grep 可追加。

**How to apply**：MVP 只需 `solve` 和 `batch` 两个命令。参数配置全部通过命令行 flags 或 YAML 文件传入。

---

## 6. 用户策略：先重度后普及

**决策**：早期只服务物理竞赛教练和技术用户。门槛降低（TUI、GUI、线上联动）放在解析质量稳定之后。

**Why**：重度用户动机最强、题库最丰富、反馈最专业。先在他们身上快速迭代核心能力，比一开始追求易用性更高效。
且这些用户能容忍命令行操作——不需要在 v1 就解决 UX 问题。

**How to apply**：初期不纠结输出格式的美观程度。README 写清楚命令行用法即可。
