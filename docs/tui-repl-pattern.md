# TUI 模式 3：命令 REPL (Read-Eval-Print Loop)

## 概述

类似 Claude Code、`psql`、`ipython` 的交互式命令环境。一个提示符 `>` 接收命令，执行后反馈结果，保持会话状态。适合**高级用户、快速操作、可组合的命令链**。

## 参考工具

| 工具 | 提示符 | 特点 |
|------|--------|------|
| Claude Code | `>` | 斜杠命令 `/plan` `/review`，自然语言 + 命令混合 |
| `psql` | `=#` | 反斜杠元命令 `\d` `\dt`，SQL 直输，续行 `-#` |
| `ipython` | `In [1]:` | `%magic` 命令，`!shell` 逃逸，`?` 自省 |
| `radian` (R) | `>` | 语法高亮输入，自动补全，多行编辑 |
| `evans` (gRPC) | `>` | 反射式服务调用，自动发现 RPC 方法 |

## Python 选型

- **prompt_toolkit**: `PromptSession` + 自定义 `Completer`(命令补全) + `Lexer`(语法高亮) + `KeyBindings`
- **Textual 内嵌**: 可以在 Dashboard 内放一个 command input 条，Textual 本身不适合做 REPL 主模式

## 优缺点

| 优点 | 缺点 |
|------|------|
| 键盘流，操作速度最快 | 新用户不知道有哪些命令 |
| 管道组合，自然表达复杂流程 | 需要实现完整的补全/帮助系统 |
| 会话状态，上下文不丢失 | 不适合长时间监控（没有实时刷新） |
| 实现复杂度中等（prompt_toolkit） | 表格/图形输出能力有限 |
| `/help` 自文档化，命令树清晰 | 错误提示需要仔细设计 |

## 如何应对"加新功能"

REPL 模式下这是**最自然**的：

1. **命令即功能** — 新功能 = 新命令(或子命令)，加到 completer tree 即可，无需改布局
2. **自动发现** — 用户输 `/help` 自动列出所有命令；新命令自动出现
3. **上下文补全** — 补全器动态发现可用命令，新命令自然融入
4. **无 UI 负担** — REPL 就是单行提示符 + 命令树，复杂度在命令定义而非 UI

> 这正好回应你的需求："加新功能还要修改对应的 TUI" — 在 REPL 模式下，加功能就是注册命令 + 注册补全规则，基本不需要"修改 UI"。

## 适合 cpho 的场景

- 临时快速操作（OCR 这个文件、给这道题加个标签）
- 组合查询（查 2024 年力学题中涉及能量守恒的）
- 脚本化/批量（管道式串联多个命令）
- 高级用户日常使用

## 不适合的场景

- 浏览大量题目（不如 Dashboard 直观）
- 实时监控处理进度（REPL 是拉取式不是推送式）
- 第一次使用的用户（需要先学命令）
