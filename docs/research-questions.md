# 调研问题

> 项目早期需要回答的关键技术问题。每个问题都是后续 spike 或 research 阶段的输入。

---

## 1. Agent 基座框架选型

**为什么重要**：决定了整个项目的起点高度。选对了省 80% 的基础工作，选错了后面要推倒重来。

待对比的维度：
- 架构可定制性（能否插入自定义的物理竞赛解析逻辑）
- 开源协议（MIT/BSD/Apache，确保可以商用和再分发）
- 社区活跃度和维护状态
- Python 版本兼容性
- 是否已有 prompt 模板管理、模型路由、结构化输出等基础能力

候选方向：基于成熟 CLI agent 框架定制 vs 使用轻量管线库自行编排

---

## 2. 本地 OCR 方案

**为什么重要**：这是整个管线的入口。OCR 质量直接决定了后续 AI 解析的天花板。
物理竞赛题目含有大量 LaTeX 公式和中文混合排版，不是普通 OCR 能处理的。

需要评估：
- 中英文混合 + LaTeX 公式的识别精度
- 扫描版试卷（图片型 PDF、照片）的处理能力
- 是否需要 GPU 加速
- 安装和使用的复杂度（用户能否一行命令搞定）
- 是否需要联网（本地优先原则）

---

## 3. Prompt 管理和版本控制

**为什么重要**：prompt 是这个产品最核心的"源代码"。
物理教研老师需要能改 prompt 而不碰代码。每次 prompt 变更需要有版本记录和回滚能力。

需要回答：
- Markdown 文件 + frontmatter 元数据是否是最佳格式
- 模板变量插值（题目文本、小问编号、前置推导结果）用什么方案最简洁
- 如何在不引入重型框架的前提下做到 prompt 版本追踪

---

## 4. 多步骤 Agent 管线的本地调度

**为什么重要**：解析一道题需要多个步骤（OCR → 推导 Q1 → 推导 Q2 → 物理图景 → 综合）。
有些步骤有依赖关系（Q2 依赖 Q1 的结果），有些可以并行。
线上版可以用 Postgres + SSE 搞异步状态机，本地版需要一个更简单但不简陋的方案。

需要回答：
- 不需要 Postgres/Redis 的前提下，任务 DAG 的调度怎么做
- 中间结果（Blackboard/Scratchpad）怎么在步骤间传递
- 并发和超时怎么处理

---

## 5. CLI ↔ 线上平台联动接口设计

**为什么重要**：虽然 v1 是纯本地工具，但架构上需要为未来联动预留空间。
现在不做，后面再打洞成本很高。

需要回答：
- 未来 CLI 调好的配置如何同步到线上
- 线上跑的解析结果如何拉到本地对比
- 是否需要 CLI 端的用户认证机制
- 最少需要哪些 API endpoint
