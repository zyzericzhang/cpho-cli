## 一、整体流程与 Skill 间衔接

### 【确定设计】
- **Solve 优先于其他 Skill**：考虑答案错误的情况，应先进行 solve，再开始别的 skill，比如 explain。
- **Solve 的定位澄清**：solve 不是去解题，而是挑出题目问题，给之后的 skill 做讲解时，让他们在正确基础上进行讲解，是给标准答案挑错。
- **核心功能定位**：Explain、找同类题、组卷，index 是核心功能。
- **组卷依赖链**：组卷的 skill 可以接在"找同类题目 skill"之后运行；必须有 index 之后运行。

## 二、Solve Skill

### 【确定设计】
- 先 solve，再开始别的 skill（如 explain）。
- Solve 是"给标准答案挑错"，不是去解题。
- **错误记录**：solve 需要把题目错误长期记录，写成 tag 形式。

## 三、Explain Skill

### 【确定设计】
- **Prompt 清晰原则**：Explain 这个 skill 的重要设计 prompt 的原则是清晰。
- **讲解顺序**：总是先用几句非常清晰的话把物理图像和架构描述清楚，再推导；总是把推导逻辑讲清楚——就是每一步怎么来的，再进行完整推导。
- **物理优先**：以物理为主，以数学为辅。
- **先看整道题**：讲解应当先看整道题，而不是一开始就直接拆 contacts，或者是在最后总结的时候——每个 Agent 或每个 LM 调用都返回之后需要进行总结。
- **首段固定内容**：Explain 输出的第一段话总是对于整道题目思路和物理图像的描述。
- **超越原答案的推导**：除了在原文解析答案上进行讲解，还需要想原来答案有没有比原来答案逻辑更清晰的数学处理推导步骤。如果有，需要分版目地写出来——一个栏目可能就是推导，一个栏目可能就是启发性的一些别的思路，要像写标准答案一样写出来。
- **句子级 explain**：还要对于句子的 explain。
- **回写 Index**：Explain 可以让用户选择在 explain 的基础上重新进行 index，把 explain 过程中发现的一些 tag 可以写进去，且用户可以自己写。
- **多 Tone 支持**：explain 可以选择 overall tone，提示词可以写好几版，对应不同 tone。用户可以选择多个 tone 进行讲解，结果生成好几版的讲解。
  - **Tone 1 · 讲解老师型**：把讲解变得有引导性，比如用"我们看"这类话，可以加入设问"什么什么是什么"，进行主动提问，然后自问自答，总体来说要像老师讲课的风格。
  - **Tone 2 · 知识点密集型**：把知识完整讲述，不关注引导，关注内容和物理推导；把物理思维和推导逻辑有序放在数学推导前面，且数学推导足够详细。
  - **Tone 3 · 简短型**：不进行完整视觉推导，只陈述最短和最重要的物理过程和推导逻辑。

### 【大致思路，未敲定】
- Explain 需要分为几个部分（具体几部分、如何切分未敲定）。
- 由于新增"超越原答案的推导/启发思路/句子 explain"等分栏目需求，**现在的架构可能需要调整**。

## 五、主动提问 Skill

### 【确定设计】
- 有一个 skill 是主动向人提问，看是否理解，它是连续对话的。
- **设计敲定**：是去寻找这道题的关键点、步骤，深挖关键处理。
- **输出形式**：提问一次生成一个 markdown 文件，存放位置选择和之前讲的方式相同，要用户输入 path。
- **文件结构**：前半部分是所有问题，后半部分是所有问题的解答。

## 六、Index Skill

### 【确定设计】
- 是核心功能之一。
- **拆分要求**：index 拆题目和答案都要拆。
- **与 Explain 联动**：Explain 时也是需要题目和答案都要的，这时候就要用 index 的结果了。
- **可由 Explain 回写 tag**（见第三节）。

### 【公开提问】
- **试卷与答案匹配**：index 的时候是不是需要把试卷和对应的答案匹配上？
- **tag 存放位置**：index 的 tag 存放位置——比如我的大物理竞赛文件夹里有很多子文件夹，如果把 workspace 设在某个子文件夹，index 出来的内容存在小文件夹里不就乱了吗？这个需要进行设计。

## 七、组卷 Skill

### 【确定设计】
- **运行时机**：可以接在"找同类题目 skill"之后运行；必须有 index 之后运行。
- **输出格式**：生成的是 PDF。
- **题目选择方式**：用户可以选择哪几道题目，或者让组卷 skill 自行选择，可以独立来。
- **编排文件**：用户需要以题号为编排，提供题目总数，自动生成一个文件，每个题号下可选填题目 ID 或者 pass，可填题目分类和大体要求。
- **排版**：出来的试卷一页一道题，答案和试卷分开。

---

## 八、第三方 Skill 与扩展机制

### 【确定设计】
- **自然语言生成 Skill 暂时不做**，之后再说。
- **用户扩展方式**：用户可以改代码，自行添加 skill，但是不能那么灵活。
- **架构复用**：好处是上述提到的 skill、skill 以及原先提到过的 skill 可以灵活一点。不一定要保持同一个接口，但尽量如果可以就用同一个底层，这样就不用太多重复代码。

---

## 九、通用能力：导出、显示、依赖库

### 【确定设计】
- **Markdown 导出（所有 Skill）**：Explain 的输出可能很长，应该对所有 skill 支持导出 markdown 文件。
- **路径与命名**：文件存放位置由用户输入 path；文件标题必须有"试觉名"（题目名），用户可以命名；输入 path 可对每个文件有默认值，用户可以调整。
- **运行过程显示**：每一个 skill 运行后都要有运行过程的显示，类似于 cloud code，需要有这个 skill 进行到哪一步了，现在进行什么，有一个较为完整的显示。
- **优先复用开源库**：上述很多功能，比如说生成 PDF，可以在 GitHub 上面找一些开源的库。如果是一些非常基础的一些普遍的工具，比如刚刚提到的 PDF 生成，尽量在调研之后找到开源库进行二次开发，不要完整写那些最基本的东西。
